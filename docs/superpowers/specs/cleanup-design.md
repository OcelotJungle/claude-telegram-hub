# telegram-hub: `/cleanup` — сжать контекст, убрать накопившиеся скиллы и завершить сессию

Основа: `hub-iteration-2-design.md`, раздел 4 (автозапуск, `/run`, `/stop`).

Звук служебных сообщений: информационные сообщения бота, команды и успешные результаты идут без звука;
предупреждения и ошибки — со звуком. Запросы разрешения и опросы, которым нужен ответ пользователя,
тоже идут со звуком. Это правило не меняет звук текста агента и завершения его хода.

## Зачем

Claude Code запоминает каждый скилл, вызванный в сессии, и после каждого компакта заново кладёт их все
в контекст: от последнего вызванного к первому, до 25k токенов на все и до 5k на один. Убрать скилл
из этого списка можно только через `/clear`, но `/clear` начинает новую сессию и новую тему.

В долгих сессиях это заметный расход токенов: скиллы, вызванные в начале работы, после каждого
компакта перечитываются на каждом запросе до конца сессии.

`/cleanup` в теме убирает эти скиллы и завершает сессию. Следующий запуск — та же сессия: тот же id,
та же тема, та же история.

## Как это устроено в Claude Code (по коду бинарника)

- Реестр вызванных скиллов живёт в памяти процесса (`invokedSkills`: `record` / `forget` /
  `forgetAll`). `forgetAll` вызывается только при `/clear`.
- После компакта Claude Code пишет в транскрипт такую запись:
  `{"type":"attachment","attachment":{"type":"invoked_skills","skills":[{"name","path","content"},…]},…}`.
  Её содержимое попадает в контекст модели.
- При `--resume` реестр собирается заново из записей `invoked_skills` в загруженных сообщениях:
  `record(name, path, content)` вызывается для каждого элемента `skills`.

Отсюда способ:

1. Компакт.
2. Остановить процесс.
3. В транскрипте опустошить `skills` у записей `invoked_skills`.
4. Следующий запуск (`/run` или сообщение в тему) идёт с `--resume`.

После этого скиллов нет ни в контексте, ни в реестре: в контексте они были только во вложении после
компакта. Следующий компакт их не вернёт. Если скилл понадобится снова, агент сам вызовет его через
Skill.

## Поведение

### Команда

`/cleanup [указания]` в теме. Указания необязательны и уходят в компакт, как у `/compact`.

В меню бота: `cleanup` — «Сжать контекст, убрать накопившиеся скиллы и завершить сессию».

### Последовательность

Это `/stop` с двумя отличиями:

- компакт делается **всегда**, а не только при контексте больше 120k. Без компакта скиллы остаются в
  контексте сообщениями, и правка транскрипта их оттуда не уберёт;
- после остановки правится транскрипт.

Сессия после этого остаётся завершённой. Каждое сообщение, пришедшее в тему во время cleanup, после
любого исхода cleanup идёт обычным путём сообщения в тему остановленной сессии: при настроенном
автозапуске сессия запускается как у `/run`, с тем же аккаунтом, шаблоном `launch` и id. Удержанные
сообщения лежат в памяти хаба и уходят по порядку; пока они передаются, новое сообщение темы встаёт
после старых. При сбое доставки действует стандартный путь (`sendHeld`). Число удержанных сообщений
не ограничено: ни при /cleanup, ни при запуске сессии ничего не отбрасывается.

По шагам:

1. Хаб ставит модулю окна команду `cleanup`. Её забирает только модуль, который спрашивает
   `GET /commands?…&cleanup=1`. Модуль старой версии её не забирает, и через `COMMAND_PICKUP_MS` хаб
   пишет обычное «⚠️ /cleanup не выполнена: окно не забрало её за N с.». Сессия не
   трогается.
2. Модуль тихо пишет в тему «🧹 Уборка на очереди.». Когда начинается её компакт, то же сообщение меняется на «🧹 Уборка выполняется…». Если попытка уступила начинающемуся ходу, сообщение возвращается к «🧹 Уборка на очереди.» до следующей попытки. Дальше он ждёт уже идущие компакты и делает свой, через ту же очередь, что
   `/compact` и `/stop`: между ходами, до 3 попыток.
3. Модуль сообщает итог хабу через `POST /cleanup` с телом `{ sessionId, id, before?, after?, error? }`.
   `before` и `after` — токены контекста до и после компакта. Хаб пишет `before` в лог; в итог ни то,
   ни другое не идёт. Своё «✅ Компакт выполнен.» в тему модуль не пишет: итог напишет
   хаб, редактируя сообщение о постановке при успехе. Итог компакта хаб ждёт не дольше `CLEANUP_COMPACT_MS = 600_000` с постановки команды. Не
   дождался: громко «⚠️ Уборка не выполнена: компакт не закончился за 10 мин», cleanup
   забыт. Итог, пришедший позже, хаб пропускает и пишет об этом в лог.
4. Если компакт упал, приходит `error`. Хаб громко пишет «⚠️ Уборка не выполнена: компакт не
   удался: …», забывает cleanup, а транскрипт и окно не трогает. Компакт, который
   модуль пропустил (например, контекст пуст), тоже приходит как `error` с причиной пропуска.
5. Если компакт удался, хаб завершает окно, как при `/stop`: WS-сообщение `terminate`, тот же
   `STOP_TIMEOUT_MS`. Перед тем как убить claude.exe, плагин сообщает хабу его pid:
   `{ type: "exiting", pid }`.
6. Правку можно начинать, только когда процесс Claude Code завершился: он дописывает файл.
   Закрытия WS для этого мало. Хаб ждёт, пока pid из `exiting` перестанет существовать (опрос
   `process.kill(pid, 0)`) через общий `exit-gate.ts`. `CLEANUP_EXIT_MS = 30_000` ограничивает
   ожидание уборки, но не снимает барьер запуска на живом процессе. Все запуски проходят через
   этот барьер в `launch()`, независимо от команды или источника сообщения.
   - Pid не пришёл, например от плагина старой версии: после закрытия WS хаб ждёт
     `MAX_RECONNECT_PAUSE_MS + EXIT_POLL_MS`. Максимальная пауза reconnect с jitter берётся из
     общей с плагином константы; окно успевает вернуться до любого нового запуска.
   - Процесс не завершился за `CLEANUP_EXIT_MS`: громко «⚠️ Уборка не выполнена: Claude Code не
     завершился». Транскрипт не правится; накопленные сообщения продолжают обычный путь сообщения
     остановленной сессии через общий барьер: они сохраняются, запуска нет до выхода процесса.
   - Если за это время окно сессии подключилось снова, ожидание кончается сразу: громко «⚠️ Уборка
     не выполнена: сессия снова открыта». Транскрипт не правится, накопленные сообщения уходят в это
     окно, как после запуска.
7. Хаб правит транскрипт (см. ниже) и пишет итог: при успехе он редактирует сообщение о постановке; если
   сессия остаётся завершённой, отдельным уведомлением приходит «⏹ Сессия завершена». Если правка упала с ошибкой, итог —
   «⚠️ Уборка не выполнена: <ошибка>».
8. Если в тему пришли сообщения, хаб запускает сессию ради них тем же путём, что `/run`, с теми же
   сообщениями и обычным уведомлением о запуске. Если окно сессии подключилось, пока шла правка, второй раз сессия не запускается: итог
   пишется, накопленные сообщения уходят в это окно. Так же поступает любой запуск: при открытом окне
   сессии хаб не запускает второй Claude Code на тот же транскрипт.

Во время cleanup закрытие окна само по себе не отправляет уведомление «⏹ Сессия завершена».

**Статус компакта редактирует сообщение о постановке в очередь. Итог заменяет его.** При начале хаб редактирует «🧹 Уборка на
очереди.» в «🧹 Уборка выполняется…»; при повторе после неудачи, вызванной начавшимся ходом, возвращает «🧹 Уборка на очереди.». Успешный итог редактирует сообщение в итоговую сводку; правка тихая по природе. При любом отказе, ошибке или отмене (шаги 3–8,
включая отмену через `/stop`) хаб удаляет сообщение о постановке и отправляет итог новым сообщением,
громким по правилу `notifies(kind)` (предупреждение и ошибка громкие, отмена — нет). Если результат
пришёл, пока сообщение о постановке ещё в outbox, операции остаются в одной очереди и выполняются по
порядку; Telegram `message_id` только сообщения о постановке сохраняется вместе с outbox (`messageIds`) до прихода итога, поэтому правка или удаление
разрешается и после перезапуска хаба. Если сообщение не было отправлено или его id неизвестен, итог
отправляется отдельно. Ошибка редактирования промежуточного статуса или неизвестный id пропускают этот статус без отдельного сообщения и не блокируют очередь; id остаётся для итоговой правки или удаления. Ошибка удаления не прерывает доставку итога. При успешной уборке завершённая
сессия получает отдельное уведомление «⏹ Сессия завершена»; при перезапуске приходят обычные уведомления
запуска. «Окно не забрало её» сюда не входит: модуль команду не взял, сообщения о постановке не было.

**`/compact` и компакт внутри `/stop`.** При старте компакт редактирует тихое сообщение о постановке на
«🗜 Компакт выполняется…». Успешный итог редактирует его в «✅ Компакт выполнен.». Пропуск или ошибка удаляет его и отправляет предупреждение новым громким сообщением. Для
`/stop` уведомление «⏳ После компакта завершу сессию…» превращается в «⏹ Сессия завершена»; без него
«⏹ Сессия завершена» остаётся отдельным сообщением.

Запуск ради сообщений из темы объявляется обычными уведомлениями запуска. Если сессия не запустилась,
громкое «⚠️ Сессия не запустилась за N с» приходит как обычно.

**`/stop` во время cleanup.**

- Пока идёт компакт, `/stop` завершает окно сразу и отменяет cleanup. Хаб громко пишет «⏹ Уборка
  отменена» вместо «Уборка на очереди», транскрипт не правится, сессия не запускается, при
  закрытии приходит обычное «⏹ Сессия завершена». Накопленные сообщения хаб этому окну не отдаёт:
  оно сейчас завершится, и они пропали бы. Они ждут закрытия окна и затем идут обычным путём
  сообщения в тему остановленной сессии; если автозапуск не настроен, остаются в очереди для
  следующего `/run`, а тема получает обычное уведомление о неактивной сессии. Если окно не
  завершилось за `STOP_TIMEOUT_MS`, они уходят в него.
- Если окно уже завершается после компакта, `/stop` ничего не меняет: хаб уже ждёт его закрытия, и
  cleanup идёт дальше.

**Сообщения во время cleanup.** С постановки команды, ещё пока окно живо и идёт компакт, обычные
сообщения в тему копятся в порядке прихода. После любого исхода cleanup они выходят из cleanup и
обрабатываются как новое сообщение в тему остановленной сессии: если окно осталось подключено,
сообщение идёт в него; если окна нет и настроен автозапуск, сессия запускается, а сообщение ждёт
подключения; иначе действует обычный путь неактивной сессии. Удержанные сообщения записываются на
диск и сохраняются при перезапуске хаба до передачи агенту.

- Сообщение, текст или подпись которого после начальных пробелов начинается с «!», пока окно живо,
  уходит в него сразу: это прерывание агента, и ждать конца компакта оно не должно.
- Команды модуля (`/info`, `/compact`…) идут в очередь команд, как обычно.
- Результат команды `/pwsh`, `/cmd`, `/bash` (входящее с `meta.source` «exec») копится так же, в том
  же списке и по тем же правилам доставки: иначе он начал бы ход агента, который обрежет завершение
  окна. Исключения для «!» к нему не относятся.
- При ошибке компакта, таймауте, закрытии окна до конца компакта, отмене через `/stop`, ошибке
  транскрипта, живом после таймаута процессе Claude Code и завершении хаба сообщения продолжают тот
  же обычный путь. При завершении хаба сохранённая очередь передаётся этому пути после следующего
  запуска хаба.

**Другие команды во время cleanup.**

- Повторный `/cleanup` и `/run` отвечают «⏳ Уборка уже идёт».
- `/cleanup` в незапущенной сессии отвечает «Сессия не запущена», как `/stop`.
- `/cleanup` во время `/stop` отвечает «⏳ Сессия уже завершается».

**Когда cleanup теряется.** Сессия остаётся как есть, транскрипт не правится:

- окно закрылось, пока шёл компакт (хаб громко пишет «⚠️ Уборка не выполнена: окно закрылось до конца компакта»);
- компакт не закончился за `CLEANUP_COMPACT_MS` (см. шаг 3);
- окно не завершилось за `STOP_TIMEOUT_MS` (хаб пишет обычное «⚠️ Не удалось завершить сессию…»);
- хаб перезапустили посреди cleanup.

### Итог в теме

- Убрано: «🧹 Уборка выполнена, убраны скиллы: brainstorming, writing-plans, …».
- Убирать было нечего: «🧹 Уборка выполнена.». То же, если записи `invoked_skills` есть, но списки в
  них уже пусты.
- Формат не узнан: «⚠️ Уборка не выполнена: формат транскрипта изменился (Claude Code <версия>)».

После успешного итога, если сессия остаётся завершённой, отдельным уведомлением приходит
«⏹ Сессия завершена». При запуске из-за сообщений из темы приходят обычные уведомления запуска.
Размера контекста и скиллов в итоге нет.

Откуда берутся части:

- Список имён — из **последней** записи `invoked_skills`: её написал только что сделанный компакт, и
  именно она лежит в контексте.
- Версия — поле `version` у этой записи, а если его нет, у любой записи транскрипта. Если версии нет
  нигде, скобка «(Claude Code …)» опускается.

## Правка транскрипта

Модуль: `plugin/src/hub/skill-cleanup.ts`. Чистые функции, файловые пути передаются параметрами.

- **Файл.** Правится основной транскрипт `<id>.jsonl`, транскрипты субагентов не трогаются.
  - Путь хаб запоминает из хука SessionStart (`transcript_path` в `onHook`) вместе с остальным про
    сессию в своём сторе. Запоминается только путь, имя файла в котором — `<id>.jsonl` этой сессии:
    хаб правит этот файл и не верит другому.
  - Если пути нет или файла по нему уже нет, хаб ищет `<projectsDir>/*/<id>.jsonl`, как это делает
    `sessionCwd`. Id сессии перед этим проверяется на вид uuid.
  - Не нашёл: «⚠️ Транскрипт сессии не найден, скиллы не убраны», под ним та же строка о сессии.
- **Какие записи.** Каждой записи с `type == "attachment"` и `attachment.type == "invoked_skills"`
  ставится `attachment.skills = []`. Правятся все такие записи в файле, не только последняя: так
  способ не зависит от того, с какого места `--resume` загружает историю.
- **Строка остаётся.** Строку не удалять: у записей есть `uuid`/`parentUuid`, и без строки порвётся
  цепочка.
  - Изменённая строка — это `JSON.stringify` разобранной записи с заменённым `skills`.
  - Все остальные строки, в том числе окончания строк и неполная последняя строка, остаются байт в
    байт.
  - Работа идёт с байтами, а не со строками: строка разбирается, только если в ней есть
    `"invoked_skills"`. Иначе она копируется как есть.
- **Поток.** Файлы бывают по 1.5+ ГБ, поэтому файл читается и пишется потоком, построчно. Результат
  пишется во временный файл рядом (`<id>.jsonl.cleanup-tmp`), потом атомарно заменяет исходный.
  Если менять нечего, файл не переписывается.
  - Первый проход запоминает размер файла. Во временный файл копируется ровно столько байт. Перед
    заменой размер сверяется ещё раз. Если файл вырос, его дописывает снова открытая сессия: правка
    бросается, временный файл и уже записанный откат удаляются, транскрипт остаётся как был. Хаб пишет
    «⚠️ Скиллы не убраны: транскрипт дописывается — сессия уже открыта?».
  - Windows ненадолго запрещает замену файла, который держит другой процесс (антивирус,
    индексатор). При `EPERM`, `EBUSY` или `EACCES` замена повторяется: до 10 попыток через 200 мс.
  - Если замена так и не удалась или упала любая другая часть, временный файл удаляется, откат
    тоже, исходный файл остаётся байт в байт.
- **Откат.** Исходные версии изменённых строк складываются в `<id>.cleanup-<время>.jsonl` рядом с
  транскриптом. Каждая строка этого файла — `{"line": <номер с 1>, "uuid": "…", "text": "<исходная
  строка>"}`.
  - Копия всего транскрипта не делается.
  - Хранятся последние 3 таких файла сессии, старые удаляются.
  - `restoreCleanup(transcript, backup)` возвращает файл байт в байт. Строку она заменяет, только если
    совпадают номер и `uuid`. Если хоть одна не совпала, она ничего не пишет и бросает ошибку.
- **Чужой формат.** Если у записи `invoked_skills` нет массива `attachment.skills`, или в нём есть
  элемент без строковых `name` и `content`, файл не правится совсем. Сессия всё равно запускается,
  итог — с «⚠️ формат транскрипта изменился». То же, если в записи `invoked_skills` есть байты,
  которые не читаются как UTF-8: откат из файла `<id>.cleanup-*.jsonl` не вернул бы их байт в байт.
  Строка, которая не разбирается как JSON, записью `invoked_skills` не считается и остаётся как есть.

### Не трогать

- Вложения после компакта, нужные для работы: `file`, `plan_file_reference`, `skill_listing`,
  `deferred_tools_delta`, `agent_listing_delta`, `mcp_instructions_delta`, `instructions`.
- Вывод хуков `SessionStart:compact`, например добавленный хуком контекст: он приходит заново при каждом старте.

## Проверка

1. Тест на копии большого транскрипта. После правки отличаются только строки
   `invoked_skills`, у них `skills: []`. Число строк и все `uuid` те же, JSON каждой строки валиден.
   Транскрипт большой, поэтому тест ручной, через скрипт `scripts/cleanup-check.ts <путь>` на копии.
   Скрипт получает уже сделанную копию. Он запоминает её исходные байты, правит, сверяет строки,
   откатывает и проверяет, что откат вернул файл байт в байт. Путь внутри `~/.claude/projects` и
   файл с именем `<uuid>.jsonl` он не принимает, чтобы не задеть живой транскрипт. Те же проверки идут автотестом на собранном файле.
2. Откат из `<id>.cleanup-*.jsonl` возвращает файл байт в байт (автотест).
3. Хаб: `/cleanup` проходит весь путь на фейках: команда модулю, компакт, `exiting`, закрытие,
   правка, итог, запуск. Отдельно проверяются ошибки: компакт упал, старый модуль, процесс не
   завершился, `/stop` во время cleanup, окно сессии подключилось во время ожидания процесса или во
   время правки.
4. README: команда в списке команд темы.
