# claude-telegram-hub — дизайн

Платформенный слой описан в `rig-integration-design.md`. На Linux `/bash` запускает
`bash` из PATH как login-shell, `/pwsh` и `/cmd` скрыты и отвечают о недоступности.
Звука завершения хода в терминале нет. Служба пользователя `telegram-hub.service` запускает
хаб с `--always-on`, `Restart=always`, `KillMode=process` и установкой пакетов через
`--frozen-lockfile`; SIGTERM вызывает обычный `stop()`. Без cswap `/run` использует
обычный Claude без номера аккаунта. Для автозапуска на Linux используется tmux,
проверки метасимволов CMD применяются только к шаблону с первым элементом cmd/cmd.exe.

Команды машины `/feature` и `/rig` принимает хаб от `allowFrom` в General и в темах
сессий, без передачи агенту. Состояние фич поступает из JSON rig; конфиг хаба не меняется.
Изменяющие команды используют detached runner, файловые логи и карточки, отдельные от
сессий. Ответы General и подтверждения отключения Telegram сохраняются на диск с повторами.
События читаются раз в 5 секунд по байтовому смещению; смещение фиксируется после доставки.
Перезапуск на обновление ждёт всех условий простоя из `rig-integration-design.md`,
пишет маркер и синхронно выходит с кодом 75. После успешного getMe записывается готовность.
Без rig хаб работает как прежде, новые команды объясняют его отсутствие.

Звук служебных сообщений: информационные сообщения бота, команды и успешные результаты идут без звука;
предупреждения и ошибки — со звуком. Запросы разрешения и опросы, которым нужен ответ пользователя,
тоже идут со звуком. Это правило не меняет звук текста агента и завершения его хода.

## Цель

Один Telegram-бот, через который любая сессия Claude Code — с любого аккаунта `cswap`, в любом из
параллельно открытых окон — может общаться с пользователем в обе стороны. Пользователь отвечает
с телефона, когда не за компьютером.

## Требования

1. **Супергруппа с темами.** Одна тема = одна сессия. Название темы: `<проект> · <название сессии>`,
   больше ничего (ни аккаунта, ни времени).
2. **Тема создаётся лениво.** Окно, запущенное в терминале, получает тему при первом сообщении,
   которое должно уйти в тему (текст агента, вопрос, файл, карточка). Явная команда «пиши мне в Телеграм»
   (`tg_enable`) создаёт тему сразу, если её ещё нет.
3. **Сессия = тема навсегда.** Сессии долгоживущие (одна задача + все доработки, регулярный компакт).
   После `--resume` сессия привязывается к той же теме. Тему не закрывать и не удалять никогда.
4. **Режим Telegram:**
   - включается явной командой пользователя в сессии (`tg_enable`);
   - для окна, запущенного в терминале (`CLAUDE_CODE_ENTRYPOINT=cli`), хаб по умолчанию включает
     режим при подключении, смене сессии и reconnect. Окна других запусков (SDK и прочие) сами не
     включаются;
   - выключается только явной командой (`tg_disable`); ввод в терминале режим не меняет;
   - режим хранится в записи сессии. `tg_disable` запоминается и не сбрасывается при reconnect или
     переходе окна к этой сессии, пока пользователь сам не включит режим (`tg_enable` или сообщением
     в тему). Переход окна к другой сессии не меняет режим прежней;
   - при смене сессии плагин сообщает хабу её заголовок и entrypoint окна. Плагин принимает режим
     от хаба, который применяет то же правило, что и при hello;
   - включается автоматически, когда пользователь пишет в тему сессии — без какой-либо команды
     в самой сессии.
5. **Что попадает в тему:**
   - промежуточный текст агента по ходу работы — **без уведомления** (`disable_notification`);
   - вопрос к пользователю и сообщение о завершении задачи — **с уведомлением**, текст целиком.
   Решение «done / ask / ничего» принимает Stop-хук (`turn-end-design.md`), а не агент.
   Звуковой сигнал в терминале не зависит от режима Telegram.
6. **Запросы разрешений:** подтверждать из Telegram не нужно (пользователь подключится к машине
   удалённо; агент почти всегда в авторежиме). В тему приходит сообщение, что требуется
   подтверждение.
7. **Сообщение в тему закрытой сессии:** бот отвечает «сессия сейчас не активна».
8. **Сообщения вне тем** (General, личка бота, чужие чаты, посторонние) — игнорировать,
   кроме команд машины `/feature` и `/rig` от `allowFrom` в General.
9. **Никаких постоянных служб.** Хаб живёт, пока открыто хотя бы одно окно.
10. **Закрытие любого окна, включая то, что подняло хаб, не ломает остальные.** Ни одно окно не
    должно терять бота до перезапуска терминала.
11. Не требовать env-переменных при каждом запуске.

## Почему не официальный плагин `telegram@claude-plugins-official`

- Каждый экземпляр `server.ts` при старте убивает предыдущий поллер (`bot.pid`) — параллельные окна
  отбирают бота друг у друга; сообщения получает последнее запущенное.
- Нет тем, нет маршрутизации по сессиям.
- Хранит состояние в `${CLAUDE_CONFIG_DIR}/channels/telegram` — у `cswap run` это папка профиля
  (`~/.claude-swap-backup/sessions/<N>-<email>`), а не `~/.claude`.

Берём его как основу (bun + `@modelcontextprotocol/sdk` + `grammy`, capability `claude/channel`,
доставка входящих через `notifications/claude/channel`, приём `permission_request`), исходник — `server.ts` официального плагина из кеша плагинов Claude Code. Официальный плагин после
внедрения отключается во всех профилях.

## Архитектура

```
 окно A (акк 1)          окно B (акк 2)          окно C
 claude --channels       claude --channels       ...
   └─ плагин telegram-hub        └─ плагин telegram-hub
        │  (сессия A)           │  (сессия B)
        └──────── localhost IPC ┘
                     │
                 ХАБ (один на машину, отдельный процесс)
                     │  getUpdates / sendMessage / createForumTopic
                 Telegram Bot API ── супергруппа с темами
```

### Компоненты

**Плагин `telegram-hub`** — MCP-сервер, по экземпляру на окно. Знает ID своей сессии из
`CLAUDE_CODE_SESSION_ID`. С Telegram напрямую не говорит — только с хабом.
Отвечает за: связь с хабом, слежение за файлом переписки своей сессии, доставку входящих в сессию,
пересылку запросов разрешений.

Инструменты агента:
- `tg_enable` — включить режим: хаб создаёт тему (если её ещё нет) или берёт существующую.
- `tg_disable` — выключить режим; такое выключение окно само не отменяет.
- `download_attachment(file_id)` — скачать файл/фото, присланные в тему.
- `tg_send_file(paths, caption?, as_document?)` — отправить в тему файлы (см. «Отправка файлов»).
- `tg_before_question` — разделитель перед `AskUserQuestion`: ничего не делает, только отделяет шаг с
  объяснением от шага с вопросом, чтобы объяснение пришло в тему над опросом (см.
  `questions-design.md`, «Текст перед вопросом»).

Отдельного инструмента «ответить» нет: весь текст агента доставляется пересылкой (см. ниже).

Модуль function hooks плагина выполняет команды из темы (см. «Команды из темы»).

**Хаб** — единственный процесс, который опрашивает бота. Создаёт темы, маршрутизирует входящие
по `message_thread_id` → сессия, отправляет исходящие, держит таблицу сессий.

**Состояние** — в `~/.claude/channels/telegram-hub/` (общая папка, не профиль `cswap`; путь не зависит от
`CLAUDE_CONFIG_DIR`, чтобы все аккаунты видели одно и то же):
- `.env` — `TELEGRAM_BOT_TOKEN` (сейчас лежит в `~/.claude/channels/telegram/.env`, перенести);
- `config.json` — `groupId`, `allowFrom` (например `["123456789"]`);
- `sessions.json` — `sessionId → { topicId, title, project, enabled, disabledByUser }`; пишет только хаб.
  `topicId` нет, пока тема не создана; `disabledByUser` есть, пока пользователь выключил режим явно;
- `hub.log`, `inbox/` для скачанных вложений.

### Потоки данных

**Включение.** Пользователь просит → агент вызывает `tg_enable` → плагин передаёт хабу `sessionId`,
`cwd` и путь к файлу переписки → хаб:
- сессия есть в `sessions.json` → `enabled = true`, сбрасывается `disabledByUser`; тема та же,
  если она есть (`topicId`), иначе создаётся сейчас (`createForumTopic`);
- сессии нет → `createForumTopic("<проект> · <название>")`, запись в таблицу, `enabled = true`.

**Окно терминала.** Плагин передаёт в `hello` `CLAUDE_CODE_ENTRYPOINT` и название сессии сейчас.
Хаб: `entrypoint = cli` и записи нет → запись с `enabled = true` и без темы; запись выключена, но
не явно (`disabledByUser` нет) → `enabled = true`; явно выключенная, а также любой другой `entrypoint`
→ без изменений. Тема такой сессии появляется при первом сообщении в неё (см. «Пересылка текста агента»).

Проект — имя папки `cwd`. Название сессии — из файла переписки: имя из `/rename`, если есть
(запись `custom-title`), иначе автоназвание
(`{"type":"ai-title","aiTitle":...}` — подтверждено). Если название сессии позже изменилось —
хаб переименовывает тему (`editForumTopic`). Пока темы нет, новое название только запоминается и
попадает в название темы при её создании.

**Входящее в тему.** Хаб получает апдейт:
- отправитель не в `allowFrom`, чат не `groupId` → игнор; в General проходят только `/feature` и `/rig`;
- тема не найдена в таблице → игнор;
- окно сессии не подключено к хабу → ответ в тему «сессия сейчас не активна»;
- иначе → `enabled = true` (если был выключен; `disabledByUser` сбрасывается) и доставка в плагин этой сессии → плагин шлёт
  `notifications/claude/channel` (тег `<channel source="telegram-hub" ...>`). Фото/документы — как
  в официальном плагине (`image_path` / `attachment_file_id`).
- форматированное сообщение (Bot API 10.1, поле `rich_message`): так Telegram шлёт вставленный
  документ, например Markdown-файл — без `text`, деревом блоков. Хаб переводит его в Markdown:
  заголовки `#`, абзацы, списки с метками Telegram и `[x]`/`[ ]`, код в ```` ``` ````, цитаты `>`,
  таблицы GFM, `**жирный**`, `*курсив*`, `~~зачёркнутый~~`, `` `код` ``, ссылки `[текст](url)`,
  формулы `$…$`. Медиа остаются на своём месте в тексте. Фото хаб скачивает в `inbox`, как фото-сообщение:
  «(photo: путь) подпись». Остальные файлы и фото, которое не скачалось, называются своим `file_id`
  для `download_attachment`: «(document: имя, file_id: …)», «(video, file_id: …)». Неизвестный вид
  блока или текста — его текст;
- ответ на сообщение идёт перед текстом, как его показывает Telegram: метка `[reply to your message]`
  (ответ этому боту, по его id из `getMe`), `[reply to the user's own message]` или
  `[reply to a message from <имя>]` (так же и другие боты), затем оригинал строками `> `, потом пустая
  строка и текст. Если текста нет (одинокий `!`), остаётся один ответ. Текст оригинала длиннее 300 символов (пометка
  медиа не считается, эмодзи не режется) обрезается, и под ним стоит `(message shortened)`.
  У медиа в оригинале — пометка вида («(photo)», «(document: имя)», «(voice message)») и подпись,
  ничего не скачивается. Цитата из сообщения даёт `[quote from …]` и идёт целиком. Ответ на
  сообщение из другого чата — `[reply to a message from another chat: <источник>]` и цитата.
  Служебное сообщение темы (корень, на который «отвечает» каждое сообщение темы) ответом не
  считается;
- пересланное сообщение начинается строкой `[forwarded from <имя>]`: пользователь, скрытый
  пользователь, чат или канал (с подписью автора, если есть); неизвестный вид источника —
  `[forwarded]`. Пересланное сообщение на `!` прерыванием не считается: это чужой текст;
- прерывание: сообщение, чей собственный текст или подпись начинается с `!` (не пересланное),
  прерывает работающего агента. `!` — сигнал только для хаба: хаб убирает его и пробелы после него
  из текста и отправляет окну уведомление с флагом `interrupt: true`. Плагин прерывает агента,
  только если флаг есть и агент работает; текст на `!` без флага (например, вставленный документ)
  приходит обычным сообщением. Одинокий `!` даёт прерывание с пустым сообщением. Свои проверки на
  `!` (сразу в окно во время `/cleanup`, новая пачка) хаб делает по исходному тексту из Telegram.
  После обновления на эту схему надо перезапустить и хаб, и окна: старое окно флаг не знает и не
  прерывает;
- сообщения, присланные вместе (альбом, несколько пересланных и текст к ним), приходят агенту одним
  уведомлением. Хаб копит сообщения темы и отправляет пачку, когда новых нет 1 с, но не позже 10 с
  после первого. Сообщения в уведомлении разделены пустой строкой. Файлы названы в тексте после
  текста сообщения: фото — «(photo: путь)», остальное — «(document: имя, file_id: …)» и т. п.
  Мета (чат, пользователь, время) берётся из первого сообщения. Пачка из одного сообщения идёт как раньше, с вложением в мете.
  Команда модуля и команда хаба сначала отправляют ждущую пачку, потом выполняются. Сообщение на `!`
  отправляет ждущую пачку и начинает новую: прервать агента может только первое сообщение пачки. ✍ ставится на
  каждое сообщение пачки; плагин сообщает о первом, и хаб снимает ✍ со всех. Сообщения, придержанные
  на время запуска или `/cleanup`, склеиваются так же: подряд идущие идут одной пачкой; ждущая в это
  время пачка встаёт среди них в порядке прихода. Если окно закрылось, пока пачка ждала, её
  сообщения идут как в неактивную сессию (придержать для запуска, запустить или сказать «не
  активна»). При остановке хаб сначала перестаёт брать обновления, потом отправляет все ждущие пачки;
- сообщение без содержимого (служебное) → игнор; в лог — имена его полей, чтобы новый вид
  сообщения было видно; каждое доставленное — строкой в лог: номер, тема, сессия, вид, длина и типы
  форматирования, без текста.

**Сообщение из терминала.** Режим не меняет, в том числе сообщение, набранное посреди хода. Плагин
читает такие записи из файла переписки для двух вещей: ход, который закрылся сразу после ввода,
закрывается тихо (хаб получает решение без отправки в тему), и отсчитываются 30 с для звука терминала
(`CHIME_MIN_TURN_MS`). Сообщение между ходами — запись `user` с `origin.kind:"human"`; набранное посреди
хода — запись `attachment` с `attachment.type:"queued_command"` и `attachment.origin.kind:"human"`.
Ходы начинают и сам Claude Code — фоновые задачи и Monitor (`task-notification`), сообщения из канала
(`channel`), отчёты сабагентов (`peer`); такие промпты режим тоже не трогают.

Режим выключается только явной командой `tg_disable`. При выключении плагин дочитывает файл переписки и
отправляет отложенный текст: финал законченного хода — со звуком, если Stop-хук решил, что ход финальный;
промежуточный — без звука. Хаб доставляет всё, что прислал плагин, если у сессии есть тема: решает
плагин, потому что только он знает, когда текст написан.

**Пересылка текста агента** (только пока `enabled`):
- текст ассистента — это текстовые блоки и блоки narration: блок `thinking` с непустым текстом и
  типом `narration` в подписи (`signature` — base64 protobuf, в начале строка `thinking` или
  `narration`). Claude Code показывает narration в терминале как обычный текст. Обычные thinking
  в файле пустые. Блок thinking с текстом и неизвестным типом пишется в лог предупреждением;
- текстовый блок ассистента, за которым в ходе последовал вызов инструмента, — промежуточный →
  сразу в тему без звука;
- последний текстовый блок хода отправляется только после окончания хода: со звуком, если ход
  финальный, иначе без. Как это решается — `turn-end-design.md`. Каждый текст доставляется хотя бы один раз; дубль возможен,
  только если Telegram принял сообщение, а ответ потерялся (ключа идемпотентности в Bot API нет).
- В тему идёт только текст ассистента: без вызовов инструментов, их вывода и скрытых размышлений.
  Заглушка Claude Code «No response requested.» (запись ассистента с `model: "<synthetic>"` без
  `isApiErrorMessage`) — не текст агента: в тему не идёт, ход на ней просто кончается. Других таких
  заглушек в транскриптах нет; сообщения об ошибках API тоже `<synthetic>`, но идут по своим правилам.
- Markdown агента идёт rich-сообщением только при заголовке, списке, таблице или разделителе, иначе
  обычным сообщением с форматированием; длинный текст режется на несколько (см. «Форматирование»).

**Сбой связи с API.** Связь с API не сработала — Claude Code пишет запись ассистента с
`isApiErrorMessage: true`, `error: "server_error"`, `stop_reason: "stop_sequence"`; текст бывает
такой:
- «API Error: Connection lost mid-response. The response above may be incomplete.» или «API Error:
  The response stopped arriving. …» — ответ оборвался, с `truncatedAfterOutput: true`, если часть
  уже пришла;
- «API Error: Can't reach the API server — check your internet or DNS (ENOTFOUND)», «API Error:
  Connection refused — a firewall or proxy may be blocking it…» — запрос до API не дошёл.
Такая запись — ещё не конец хода. Её же Claude Code пишет, когда оборвался лишь ответ классификатора
auto mode на вызов инструмента (вызов получает результат «classifier gave no verdict», ход идёт
дальше), и перед тем, как сам повторит запрос. Ход кончился на ней, только если следом, раньше
следующей записи ассистента, идёт `system` с `subtype: "turn_duration"` — так Claude Code закрывает
ход, когда его попытки кончились (проверено по всем доступным транскриптам: закрытые ходы и продолжившиеся
различаются так без исключений). Текст ошибки — не агента и в тему не идёт. Ход кончился на сбое, и режим
включён — плагин продолжает за человека:
- в тему без звука «🔁 Сбой связи с API — агент продолжает сам.»;
- агенту через канал (`meta`: `user: telegram-hub`, `reason: response_cut`) — по-английски: «telegram-hub: your
  last turn ended with an API connection error (…), so your last response may be missing or
  incomplete. Continue from where you stopped.»;
- не больше 10 раз подряд: счётчик сбрасывает любой другой конец хода. Каждое продолжение снова
  проходит повторы Claude Code, так что 10 раз покрывают и долгий обрыв сети. На 11-м сбое подряд —
  в тему со звуком «⚠️ Сбой связи с API 10 раз подряд — сам больше не продолжаю, жду тебя.»,
  агенту ничего; дальше молча до нормального конца хода;
- режим выключен — ничего: человек за терминалом. Сбои, записанные до запуска окна, — история.
Прочие ошибки API (`rate_limit`, `authentication_failed`, `invalid_request` — например, сработали
safeguards) — не про сеть: повтор не поможет, решает человек.

Конец хода: основной источник — хук `Stop` плагина (получает `session_id` и `transcript_path`),
запасной — `stop_reason: "end_turn"` в файле переписки.

**Форматирование.** Агент пишет Markdown (CommonMark + GFM; терминал показывает его так же). Хаб
разбирает его лексером `marked` (`plugin/src/hub/message-kind.ts`). Текст с заголовком, списком (любым,
на любой глубине), таблицей или разделителем идёт rich-сообщением (Bot API 10.1, `sendRichMessage`) в виде
дерева блоков, а не строкой `markdown`. Остальной текст (жирный, курсив, зачёркнутый, код, блоки кода,
цитаты, ссылки) идёт обычным сообщением с `entities`, каким бы длинным он ни был. Причина: Telegram не
передаёт боту цитату, когда пользователь отвечает на часть rich-сообщения бота. Свой разбор Markdown у Telegram выбрасывает незнакомые теги
(`<channel>` пропадает), склеивает строки и делает из `$…$` формулу. Блоки несут текст буквально.
Соответствие:
- заголовок → heading того же уровня, абзац → paragraph (одиночный перевод строки остаётся
  переводом), блок кода → pre с языком, цитата → blockquote, разделитель → divider;
- список → list: вложенный — внутри пункта, нумерованный — с `value` от своего начала, задачи —
  `has_checkbox`/`is_checked`;
- таблица → table с рамкой и полосами; выравнивание из разделителя, по умолчанию заголовок по
  центру, ячейки влево;
- `**…**`/`__…__` → bold, `*…*`/`_…_` → italic, `~~…~~` → strikethrough, `` `…` `` → code;
- ссылка `[текст](url)` → url, если url — `http(s)://` или `tg://`; иначе «текст (url)»; голая
  ссылка и ссылка, чей текст совпадает с url, — простым текстом (Telegram сам делает её ссылкой);
  картинка `![alt](url)` — как ссылка;
- HTML — как текст; HTML-сущности (`&amp;` и т. п.) раскрываются.

Длина. Telegram документирует предел в 32768 символов (больше — `RICH_MESSAGE_TEXT_TOO_LONG`), но
кириллицу молча обрезает около 35000 байт. Поэтому хаб режет текст между блоками верхнего уровня на
куски не больше 30000 байт исходного Markdown и не больше 500 блоков (считаются вложенные блоки,
пункты списков и строки таблиц). Ссылки-сноски `[x]: url` разбираются по всему тексту. Один блок
больше предела (огромный блок кода) идёт простым текстом с `entities` (ниже), кусками ≤ 4096.

Запасной путь — простой текст и `entities`, а не `parse_mode`: экранировать нечего, а кусок длинного
текста — это кусок простого текста с обрезанными по нему сущностями. Telegram отверг rich-сообщение —
хаб шлёт его исходник так (WARN в лог); отверг и это — без сущностей (WARN); отверг и это —
уведомление, как раньше. Подписи к файлам тоже идут так: в `sendMediaGroup` rich-сообщений нет.
Соответствие в этом пути:
- inline-форматирование — как выше, блок кода → pre с языком, цитата → blockquote (вложенная — без
  второй сущности: Telegram их не вкладывает), ссылка → text_link;
- заголовок → жирная строка; список → строки с «•» (вложенный — с отступом, «◦»), нумерованный —
  «1.», задачи — «☐»/«☑»; таблица → моноширинный блок (pre) с выровненными столбцами; разделитель →
  «———»;
- куски ≤ 4096 символов простого текста режутся по абзацам, строкам, словам; сущность на границе
  делится между кусками; суррогатная пара не режется; пробелы по краям куска срезаются.

Служебные тексты хаба (подтверждение, уведомления) не разбираются и идут простым текстом.

**Отправка файлов.** Инструмент `tg_send_file(paths: string[], caption?: string, as_document?: boolean)`:
- работает, если у сессии есть тема, даже при выключенном режиме (агент отправляет файл по явной
  просьбе); темы нет — ошибка «сначала `tg_enable`»;
- плагин до отправки проверяет: каждый путь (относительный — от `cwd`) — непустой файл не больше
  50 МБ и не из папки состояния (кроме `inbox/`); подпись после разбора Markdown — не длиннее 1024
  символов. Любая ошибка — не отправляется ничего, агент получает причину;
- тип по расширению: фото — jpg/jpeg/png/webp (больше 10 МБ — документом), видео — mp4, аудио —
  mp3/m4a, gif — анимация, остальное — документ. `as_document: true` — все файлы документами, без
  пережатия Telegram (скриншоты, где важны пиксели);
- видео: перед первой отправкой хаб узнаёт через `ffprobe` размер (с учётом поворота у роликов с
  телефона) и длительность, а `ffmpeg` делает превью — JPEG до 320 px по стороне и меньше 200 КБ,
  кадр около первой секунды, рядом с копией. Без них Telegram показывает большое видео чёрным
  квадратом без длительности, и его надо скачать, чтобы посмотреть. Хаб передаёт `width`, `height`,
  `duration`, `supports_streaming` и `thumbnail` (в альбоме — `attach://thumb<i>`). Результат
  хранится в элементе очереди и не пересчитывается при повторе. Нет `ffprobe` или файл не видео —
  видео уходит как раньше, WARN в лог; нет `ffmpeg` — без превью. Превью удаляется вместе с копией;
- альбомы: подряд идущие фото и видео — один альбом, подряд идущие документы — другой, аудио —
  третий; до 10 в альбоме и не больше 50 МБ на весь альбом (лимит Telegram — на запрос целиком,
  больше — ответ 413); одиночный элемент и анимация — отдельным сообщением. Порядок файлов
  сохраняется. Подпись — у первого отправленного сообщения (у альбома — у первого элемента,
  Telegram показывает её под альбомом);
- порядок с текстом: файлы идут через ту же очередь хаба, что и текст. Перед этим плагин дочитывает
  файл переписки и отправляет текст, написанный до вызова, — он уходит раньше файлов;
- звук: пока режим включён — без звука (итог хода придёт со звуком), выключен — со звуком;
- плагин копирует файлы в `outbox-files/<id>/` папки состояния (агент может удалить или изменить
  их сразу после вызова) и передаёт хабу как текст: с id, до подтверждения, с повтором после
  переподключения и через `spool/`. Хаб принимает пути только из `outbox-files/` и ставит в очередь
  на диске по элементу на каждую отправку Telegram — повтор после сбоя не дублирует уже ушедший
  альбом. Копии удаляются, когда их элемент покинул очередь;
- загрузка — `multipart/form-data`; время ожидания попытки растёт с размером;
- Telegram отверг фото (`PHOTO_…`, `IMAGE_PROCESS_FAILED` — например, неподходящие размеры) —
  хаб отправляет эти фото документами. 413 (Request Entity Too Large) не повторяется: альбом уходит
  по одному файлу, одиночный файл — отказ. Прочий отказ и пропавшая копия — в лог ERROR и агенту
  («<имена>: <причина>»); в тему ничего: файлы прислал агент, ему и решать (сжать, отправить
  иначе);
- инструмент ждёт, пока хаб отправит всё (до 150 с), и сообщает итог, в том числе отказ. Не
  дождался (нет сети) — сообщает, что файлы в очереди и уйдут, когда Telegram станет доступен.
  Хаб шлёт итог (`filesSent`) окну, приславшему файлы; если его нет (хаб перезапускался, окно ещё
  не переподключилось), итог ждёт `hello` этой сессии. Повтор уже отправленных файлов после
  переподключения получает итог сразу. Итог с отказом, пришедший, когда инструмент уже вернулся,
  плагин передаёт агенту через канал (`meta`: `user: telegram-hub`, `reason: files_rejected`) — по-английски:
  «telegram-hub: Telegram did not take files you sent earlier with tg_send_file: <имена>: <причина>. The
  topic was not told. Deal with it yourself: …».

**Запрос разрешения.** Плагин получает `notifications/claude/channel/permission_request` → хаб шлёт
в тему со звуком: «Нужно подтверждение: `<инструмент>` — `<описание>`». Кнопок нет, подтверждение
делается в терминале. (Официальный плагин намеренно не принимает подтверждения из групп — мы и не
принимаем.)

**Вопрос агента (`AskUserQuestion`).** При включённом режиме `PreToolUse`-хук плагина
(`src/hook/question.ts`) шлёт вопросы хабу (`POST /question`) и ждёт до 24 часов; хаб задаёт их в теме
кнопками и возвращает ответы, хук отдаёт их Claude Code как `updatedInput`. Режим выключен — диалог в
терминале. Подробно — `questions-design.md`.

**Команды из темы.** `/info`, `/compact`, `/compact <N>` — то же, что строка статуса, `/compact` и
`/autocompact N` в терминале этой сессии, `/rename <имя>` — `/rename` в терминале. Сообщения из канала Claude Code ставит в очередь с
`skipSlashCommands`, поэтому команду через канал не выполнить. Выполняет её модуль function hooks
плагина (`hooks.json` → `modules`, API раннего доступа Claude Code; есть
`$.session.usage`, `$.command.run`, хук `session.compact`).
- Хаб узнаёт команду в сообщении темы: текст `/info`, `/compact` или `/rename`, можно с
  `@<имя бота>` (с чужим именем — обычное сообщение) и аргументами. Агенту команда не доставляется,
  в контекст не попадает, режим не меняет. Прочие `/…` — обычные сообщения. Если окно закрыто,
  команды модуля запускают сессию при настроенном `launch`; команда ждёт подключения окна, затем её
  забирает модуль. Без `launch` остаётся ответ «сессия сейчас не активна».
- Хаб держит команду в памяти (не на диске: она интерактивная) и отдаёт её модулю по
  `GET /commands?session=<id>`; модуль опрашивает хаб раз в секунду, `id` сессии берёт у
  `$.session.id()` при каждом опросе (после `/clear` он другой). Модуль не забрал команду за 10 с
  (старая Claude Code, модуль не загрузился, окно ещё на старом плагине) — хаб пишет в тему со
  звуком «⚠️ /<команда> не выполнена: окно не забрало её за 10 с.»
- Ответ модуль шлёт `POST /reply {sessionId, id, text, notify}`; хаб ставит его в очередь темы как
  текст агента (Markdown); повтор с тем же `id` не дублируется.
- `/info` — `$.session.usage({ breakdown: "summary" })`: проценты пятичасового и недельного окна
  со временем до сброса («нет данных», пока в сессии не было ответа модели); контекст сейчас в
  тысячах токенов (цифра строки статуса; после компакта и до первого ответа её нет — тогда оценка
  со знаком «≈»); окно автокомпакта и порог срабатывания; сколько процентов порога занято.
  Автокомпакт выключен — так и пишется.
- Лимиты — аккаунта, а `$.session.usage().rateLimits` — из последнего ответа API этой сессии: в
  сессии, которая час молчала, они на час старше. Поэтому модуль на каждый `session.measure` (после
  каждого хода и когда окно сдвинулось на целый процент) шлёт хабу `POST /limits {sessionId, at,
  rateLimits}`, а `/info` спрашивает `GET /limits?session=<id>` — самое свежее показание сессий того
  же cswap-аккаунта (аккаунт неизвестен — только своё). Хаб держит показания в памяти. Нет ответа
  или показаний — свои цифры сессии. Показанию от 5 минут — в заголовке «**Лимиты Claude** (данные
  N мин назад)**.
- Между блоками Claude и «Контекст» `/info` показывает «**Лимиты Codex**», если `GET /codex-limits`
  вернул показание (`LimitsReading`, иначе `null`). Хаб читает `$CODEX_HOME/sessions` (по умолчанию
  `~/.codex/sessions`): до 20 rollout-файлов, новые даты первыми, внутри даты — по mtime.
  Читает JSONL с конца блоками; последнее событие `event_msg/token_count` с
  `rate_limits.limit_id: "codex"` даёт время показания из `timestamp`. `premium`, `null` и
  некорректные строки пропускаются; если показания нет, проверяется предыдущий файл.
  Результаты кешируются по пути, mtime и размеру. Окна 300 и 10080 минут — «5 часов» и «Неделя»,
  остальные — длительность в минутах; проценты округляются, `resets_at` переводится из Unix-секунд.
  После сброса — 0% без суффикса сброса. Возраст от 5 минут отображается тем же правилом, что у Claude.
  Credits не показываются; отсутствие данных или ошибка запроса убирает только блок Codex.
- После блока Codex (или после блока Claude, если Codex нет) `/info` показывает «**Лимиты волонтёров**`,
  если `GET /volunteer-limits` вернул `kind: "ok"`. Хаб запускает скрипт
  `python -I ~/.claude/tools/volunteer-models.py limits --json` (путь и команда настраиваемые через
  `HubOptions.volunteerLimitsScript` и `volunteerLimitsCommand`, таймаут 5 с через
  `volunteerLimitsTimeoutMs`). Скрипт печатает JSON с полями `checked_at`, `source`, `day_percent`,
  `reset_in_s`, `providers`. `source: "none"` → блок не показывается, `error` текстом в строке
  «Лимиты волонтёров: нет данных — <reason>». При `ok`: заголовок с возрастом от 5 минут, строка
  `День: X% (сброс через <duration>)` (после сброса — `День: 0%` без суффикса), затем провайдеры,
  каждый на своей строке: имена мапятся (openrouter→OpenRouter, requesty→Requesty, groq→Groq,
  zhipu→Zhipu, не «Z.ai»: Telegram делает из него ссылку; остальные как есть), формат
  `Имя: used/cap`. Провайдер с `cap: null` хаб отбрасывает: без лимита число не говорит, сколько
  осталось. Ошибка скрипта / таймаут /
  неверный JSON → строка ошибки. Нет данных Claude — «Лимиты Claude: нет данных — появятся после
  первого ответа модели».
- `/compact` и `/compact <указания>` — `$.command.run({ command: "compact" })`: как набранная в
  терминале, ждёт конца текущего хода. Сразу — «🗜 Компакт запущен…»; итог — из хука
  `session.compact`: «✅ Контекст сжат: 180k → 24k токенов» или причина пропуска.
  Не запустилась — причина.
- `/compact <N>` (число токенов, можно `333k`, `1m`) и `/compact auto` — `/autocompact` с этим
  значением; ответ — текст команды. Действует так же, как `/autocompact` в терминале этой сессии.
- `/rename <имя>` — `$.command.run({ command: "rename", args: "<имя>" })` с именем, как его набрали (хаб
  обрезает пробелы по краям). Как `/compact`, ждёт конца текущего хода: сразу тихое «🏷 Переименование на
  очереди.» (`awaitsResult`), успех редактирует его в «✅ /rename <имя> выполнена.», отказ `run` —
  громкое «⚠️ /rename <имя> не выполнена: <причина>» вместо него (`replaces`, kind `warning`). `/rename`
  без имени — «Напиши имя: /rename новое имя», `run` не вызывается. Хаб ничего не переименовывает сам:
  тема сменит название, когда Claude Code запишет новое название в переписку — тем же путём, что и
  любая смена названия сессии (`retitle`).
- `/mode` показывает режим этого запуска: режим успешного запуска и последующие записи transcript,
  либо запись после подключения окна (хаб запоминает размер transcript при подключении). Более
  старый режим подписан «Последний известный режим» и не запрещает переключение. Предлагаются кнопки `manual`, `auto`, `acceptEdits`, `plan`,
  `dontAsk`. `default` в transcript означает `manual`; неизвестный или запрещённый текущий режим
  показывается как есть, без отмеченной кнопки. `/mode <режим>` и кнопки принимают только эти значения
  без учёта регистра. Переключение сразу завершает окно, не вызывает модуль и не запускает компакт;
  ход обрывается. Перед завершением хаб проверяет аккаунт, cwd и команду запуска. Для неё требуется
  `{mode}` в `launch.command`, который подставляется как `--permission-mode <режим>`; отдельный элемент
  `{mode}` разворачивается в два argv элемента, а при обычном запуске удаляется. При отсутствии
  настройки или ошибке команда предупреждает, не закрывая окно и не убирая кнопки. Закрытая сессия
  запускается даже с прежним режимом. Переключение начинается до косметических запросов Telegram.
  После обрыва связи с окном хаб ждёт общего барьера выхода Claude Code в `launch()`: второй процесс
  на той же переписке её сломал бы. Барьер обязателен для всех путей запуска, включая `/run`, `/mode`,
  сообщения темы, результаты команд, `releaseHeld` и маршрут `/cleanup`. Он создаётся при закрытии
  окна с exiting pid или окна, завершаемого хабом. Неизвестный pid ждёт дольше общего максимального
  reconnect backoff с jitter; вернувшееся окно снимает барьер и отменяет смену с предупреждением
  «⚠️ Режим не сменён: сессия снова открыта». Затем
  сессия запускается с выбранным режимом, а сообщения и результаты команд за время перезапуска
  удерживаются и доставляются по порядку после готовности нового окна. С начала перезапуска
  удерживаются также ожидающие batch/replay, batch с подготовкой вложения и результаты команд;
  после асинхронной подготовки состояние проверяется повторно. Новые результаты после подключения
  входят в ту же очередь готовности. Открытые опросы заканчиваются сразу. Пока идёт ожидание, `/run` и оба варианта `/mode`
  отвечают «Сессия уже запускается». Таймаут завершения оставляет прежнее окно и отдаёт ему удержанное;
  процесс, не вышедший за `CLEANUP_EXIT_MS`, отменяет смену режима с одним предупреждением,
  но сохраняет барьер: запусков нет до выхода процесса. После выхода удержанное идёт обычным путём.
  Ошибка spawn, отказ проверок и таймаут подключения сохраняют удержанное до следующего запуска;
  тема получает число ожидающих элементов, подтверждения exec вызываются после доставки.
  `/stop` отменяет любой запуск, включая уже порождённый процесс: подключившееся окно завершается,
  удержанное ждёт его выхода и идёт обычным путём. Перезапуск пишет 🔁 без «⏹ Сессия завершена».
  Режим сохраняется только после успешного spawn; отсутствие `{mode}` при запуске с режимом — отказ.
  Обычный запуск, в том числе после `/cleanup`, очищает режим и смещение. Смещение за размером
  укороченного transcript не читается; отсутствие transcript при запуске не делает старые записи
  новее режима запуска. Поиск режима читает transcript назад блоками до записи или смещения.
- Хаб при старте регистрирует команды темы в меню бота (`setMyCommands`), сбой — WARN в лог.

### Жизненный цикл хаба и сбои

- Плагин при старте подключается к хабу на фиксированном локальном порту. Не удалось — запускает
  хаб как **отсоединённый** процесс (не дочерний окну) и подключается снова.
- Хабом становится тот, кто сумел занять порт; второй хаб при гонке сразу завершается. Два поллера
  одновременно невозможны.
- Хаб завершается через 5 минут после отключения последнего плагина, но не раньше, чем доставит
  свою очередь. Исключение — доставка заблокирована настройкой (нет токена, токен отвергнут, бота
  нет в группе, нет `groupId`): тогда хаб выходит, очередь остаётся на диске для следующего хаба.
- Закрытие окна, поднявшего хаб, хаб не затрагивает.

**Доставка не теряет сообщений и не меняет их порядок** — ни без сети, ни при падении хаба:
- плагин держит текст в памяти, пока хаб не подтвердит приём; после переподключения шлёт
  неподтверждённое заново, по порядку. Каждое сообщение несёт id и `sessionId`;
- хаб, получив текст, режет его на куски и сначала записывает в очередь на диске (`outbox.json`,
  атомарная запись), потом подтверждает. Повтор с тем же id хаб узнаёт и не ставит второй раз;
- очередь сессии отправляется строго по одному: следующий кусок уходит после того, как Telegram
  принял предыдущий. Кусок удаляется из очереди после ответа Telegram;
- сеть, 429, 5xx — повтор без ограничения по времени, пауза растёт до 30 с; в лог одна строка на
  серию сбоев и строка о восстановлении;
- блокировка настройкой (см. выше) — то же, пауза 30 с, в логе подсказка, что чинить;
- тема удалена — новая тема и повтор;
- Telegram отверг конкретное сообщение (прочие 400) — текст пишется в лог как ERROR, а вместо
  него в тему со звуком уходит «⚠️ Telegram не принял сообщение: <причина>. Текст в hub.log.»;
- хаб при старте поднимает очередь с диска и продолжает;
- входящие обновления Telegram подтверждаются следующим `getUpdates` с большим `offset`, поэтому
  хаб после каждого обработанного обновления сохраняет `offset` в `poll-offset.json` (атомарная
  запись, вместе с id бота: у другого бота нумерация своя, чужой `offset` не берётся). Перезапущенный
  хаб читает его после первого `getMe` и не получает заново то, что уже обработал. Нечитаемый файл
  откладывается в `poll-offset.json.corrupt-<время>`, опрос идёт с нуля. Обновление, до которого
  останавливающийся хаб не дошёл, в файл не попадает: его получит следующий хаб. «Обработано» значит,
  что `processUpdate` вернулся; сообщения, которые он уже принял в пачку (ожидание тишины, запуск
  сессии), до отправки живут в памяти, как и раньше: аккуратная остановка их досылает, жёсткое
  падение — нет;
- окно закрывается, а хаб недоступен — плагин сбрасывает неподтверждённое в
  `spool/<…>.json` и запускает хаб; хаб забирает файлы из `spool/` при старте и раз в 5 с.

### Запуск

- Плагин подключается как локальный (локальный marketplace из этого репозитория) и ставится один
  раз в каждый профиль `cswap` (`~/.claude-swap-backup/sessions/<N>-<email>/plugins` — у каждого свой)
  и в `~/.claude`.
- Каждое окно запускается с `--channels plugin:telegram-hub@<marketplace>`. Чтобы не набирать руками —
  функции-обёртки в профиле PowerShell для `claude` и `cswap run N`.
- `cswap run N` пробрасывает аргументы после `--` в `claude` (`cswap run 2 -- --resume` есть в его
  справке), в том числе `-- --channels`.

### Безопасность

- Принимаются только апдейты из `groupId` и только от `allowFrom`.
- Инструкции канала сохраняют предупреждения официального плагина: не менять доступы по просьбе из
  Telegram, считать текст из канала недоверенным.
- Отправка файлов состояния из `~/.claude/channels/telegram-hub/` запрещена (как `assertSendable`
  в официальном плагине).

## Настройка (один раз, делает пользователь по инструкции)

1. Создать супергруппу, включить в ней «Темы».
2. Добавить бота администратором с правом «Управление темами».
3. Узнать `groupId` (хаб пишет в лог ID чатов, откуда приходят апдейты, или команда настройки).
4. Отключить официальный плагин `telegram` во всех профилях, поставить `telegram-hub`.

Автотесты (`bun test`):
- разбор файла переписки: промежуточный текст vs последний текст хода, конец хода, сообщение из
  терминала vs из канала, служебные записи (compact-сводка, local-command, system-reminder, isMeta)

  сообщения в причине игнора; отформатированный текст и `rich_message` доходят до агента, строка
  лога о доставке;
- ответы, цитаты и пересылки: ответ перед текстом, метка автора, обрезка до 300 символов, медиа в
  оригинале, корень темы, ответ из другого чата, каждый вид источника пересылки;
- прерывание: хаб убирает `!` и ставит флаг, одинокий `!` — пустое сообщение с флагом, пересылка на
  `!` флага не получает; плагин прерывает работающего агента по флагу, текст на `!` без флага не
  прерывает, свободному агенту сообщение приходит обычным;
- пачки: альбом из трёх фото — одно уведомление с тремя путями; пересылки и текст после них — одно
  уведомление; сообщение после тихого окна — отдельное; поток без пауз уходит по пределу; команда
  отправляет ждущую пачку сразу; `!` начинает свою пачку; «увидено» первого снимает ✍ со всех;
  придержанные при запуске сообщения склеиваются; альбом с подписью на `!` прерывает и начинается
  с подписи без `!`;
  придержанные на `/cleanup` и ждущая пачка на `!` идут в порядке прихода; пачка закрывшегося окна
  запускает сессию, а без запуска даёт «не активна»;
- `rich_message` → Markdown: каждый вид блока и текста, вложенные списки, таблица, медиа с `file_id`
  и путём скачанного фото, неизвестные виды; фото для скачивания — самый большой размер каждого,
  где бы оно ни лежало; хаб скачивает их в `inbox`, а не скачавшееся остаётся с `file_id`;
- таблица сессий: повторный `tg_enable`, `--resume` (тот же ID → та же тема);
- выборы хаба: гонка двух плагинов, смерть хаба, переподключение, автозавершение;
- форматирование: каждое соответствие из «Форматирования» в обоих путях; теги, `$` и переводы строк
  остаются; нарезка rich-текста по байтам и по числу блоков; блок больше предела — простым текстом;
  нарезка с сущностями на границе; после отказа — простой текст с сущностями, потом без них;
- команды: распознавание (`@бот`, чужой бот, аргументы), не доходят до агента, отдача модулю и
  ответ в тему, 10 с без модуля, текст `/info` во всех случаях (нет лимитов, нет цифры контекста,
  автокомпакт выключен), выбор между `compact` и `autocompact`, итог компакта из хука;
- отправка файлов: проверки до отправки, тип по расширению, альбомы и их границы, подпись, порядок
  с текстом, звук по режиму, повтор после переподключения без дубля, фото документами после отказа,
  отказ и пропавшая копия, удаление копий;
- очередь доставки: долгое отсутствие сети, перезапуск хаба с непустой очередью, повтор с тем же

  доставки, `spool/` от закрытого окна;
- ввод в терминале, в том числе посреди хода, режим не выключает и текст агента продолжает идти в тему;
  промпты `task-notification`, `channel` и `peer` режим тоже не меняют;
- обрыв ответа: распознавание записи, продолжение и заметка в теме после текста ошибки, тишина при
  выключенном режиме, предел 10 подряд и сброс нормальным концом хода, обрыв до запуска окна.

Ручная проверка на настоящей группе: два окна на разных аккаунтах; закрытие окна, поднявшего хаб;
`--resume`; ответ в тему закрытой сессии; ввод в терминале не выключает режим, сообщение в теме включает его;
беззвучные и звучащие сообщения на телефоне; `/info`, `/compact` посреди хода и после, `/compact 333k`.

## Результаты предварительной проверки

Проверено экспериментом (временный плагин с MCP-сервером и хуками, `claude -p --plugin-dir`):

1. **Флаг каналов.** Скрытые флаги: `--channels <servers...>` (только одобренный allowlist) и
   `--dangerously-load-development-channels <servers...>` (неодобренные; показывает диалог
   подтверждения при старте). Формат: `plugin:<имя>@<marketplace>` или `server:<имя>`. Allowlist
   можно заменить managed-настройкой `allowedChannelPlugins: [{plugin, marketplace}]` (требует
   `channelsEnabled: true` в managed settings). Плагин из `--plugin-dir` получает marketplace
   `inline`. **Не проверено:** загрузка канала настоящим Claude — запуск с dev-флагом заблокирован
   классификатором авторежима, проверяется вручную.
2. **ID сессии в MCP-сервере** — да, `CLAUDE_CODE_SESSION_ID` выставляется для MCP-сервера плагина
   (не наследуется). `CLAUDE_CONFIG_DIR` тоже есть (у `cswap run` — папка профиля).
3. **`--resume <id>`** сохраняет ID: и MCP-сервер, и хуки видят тот же ID, запись идёт в тот же файл.
4. **Файл переписки:**
   - сообщение ассистента разбито на записи по одному блоку контента; у всех записей одного
     сообщения общий `message.id` и итоговый `stop_reason` (`tool_use` / `end_turn`); записи
     пишутся до срабатывания хука `Stop`;
   - сообщение из терминала: `type:"user"`, `origin:{kind:"human"}`, `promptSource` =
     `typed` | `queued` | `suggestion_accepted`; служебные (`isMeta`, compact-сводка
     `isCompactSummary`, local-command, task-notification, peer) — без `origin.kind:"human"`;
   - входящее из канала (по коду CLI): `isMeta:true`, `origin:{kind:"channel", server}`;
   - имя сессии: записи `custom-title` (`customTitle`), `agent-name` (`agentName`, её пишет
     `/rename` в этой версии) и `ai-title` (`aiTitle`). Приоритет: custom-title → agent-name →
     ai-title, в каждом — последняя запись.
5. **Хуки** получают JSON с `session_id`, `transcript_path`, `cwd`; `SessionStart` — ещё `source`
   (`startup` | `resume` | `clear` | `compact`), `Stop` — `last_assistant_message`.
   MCP-сервер и хуки одного окна получают одинаковый `CLAUDE_CODE_MESSAGING_SOCKET`
   (у каждого процесса claude свой) — по нему хаб связывает хук с окном.
6. Bot API (темы) проверяется вручную на настоящей группе.
7. **`cswap run N -- <args>`** пробрасывает аргументы в claude (проверено с `-p`/`--plugin-dir`).

Дополнительно: на Windows второй `Bun.serve` на занятом порту падает с `EADDRINUSE` (выборы через
порт работают); отсоединённый (`detached`) процесс, запущенный MCP-сервером, переживает завершение
claude.

### Решения по итогам проверки

- **Конец хода** — основной источник хук `Stop`, запасной — файл переписки: запись ассистента с
  `stop_reason`, отличным от `tool_use` и `null`. Записи попадают в файл раньше срабатывания хука,
  поэтому гонки «хук раньше записи» нет.
- **Смена сессии в окне** (`/clear`, `/resume` внутри окна): MCP-сервер не перезапускается,
  а `CLAUDE_CODE_SESSION_ID` у него остаётся старым. Плагин ставит хук `SessionStart`, хук шлёт
  хабу `{session_id, transcript_path, messagingSocket}`, хаб пересылает плагину этого окна.
  Плагин переключает файл переписки и отправляет хабу сообщение `session` с новой сессией,
  entrypoint окна и заголовком новой сессии. Хаб применяет общее правило подключения: для `cli`
  включает сессию, если в её записи нет `disabledByUser`; новое состояние сообщает плагину. Для
  SDK и прочих entrypoint новая запись остаётся выключенной. Запись прежней сессии не меняется;
  тема новой сессии создаётся только при первой отправке текста.
- **Путь к файлу переписки** при старте: `<CLAUDE_CONFIG_DIR>/projects/<cwd, где каждый
  не-буквенно-цифровой символ заменён на «-»>/<sessionId>.jsonl`; если такого нет — поиск
  `projects/*/<sessionId>.jsonl`; файла может ещё не быть (новая сессия) — ждём появления.
- **Чтение файла** начинается с текущего конца (история при `--resume` не пересылается); имя
  сессии для темы читается отдельным полным проходом при `tg_enable`.
- **Свои инструменты и финальный текст.** Вызов своих `tg_enable`/`tg_disable` не делает
  предшествующий текст «промежуточным». Звук в конце хода решает Stop-хук, а не агент
  (`turn-end-design.md`).
- **Разрешения** — плагин объявляет `claude/channel/permission`, чтобы получать
  `permission_request`, но ответов никогда не шлёт; сообщение уходит, только пока режим включён.
- **Хаб и Telegram** — Bot API через `fetch` без grammy (база URL настраивается — тесты
  используют поддельный сервер Bot API).
- **IPC** — WebSocket и HTTP на `127.0.0.1`, порт по умолчанию 47613; запросы с заголовком
  `Origin` (браузер) отвергаются.
- **Тема удалена вручную** (Telegram отвечает «thread not found») — хаб создаёт новую тему для
  сессии и повторяет отправку.

### Наблюдения при работе

- Часть видимого текста агента пишется в файл как блок `thinking` типа narration (см. «Пересылка
  текста агента»): таких блоков много, а обычные thinking пусты. Без их
  разбора терялась большая часть промежуточных сообщений.
- Сообщение, набранное в терминале посреди хода, — не запись `user`, а `attachment`
  `queued_command` с `origin.kind:"human"`. Уведомления о фоновых задачах приходят так же, но
  с `origin.kind:"task-notification"`.
- Хук `UserPromptSubmit` срабатывает на каждый промпт, начинающий ход, в том числе на
  `<task-notification>` от фоновых задач и Monitor. Во входе только `session_id`,
  `transcript_path`, `cwd`, `prompt_id`, `permission_mode`, `prompt` и подобное — поля
  `input_source` нет, источника промпта не видно. Запись промпта (`promptId`, `origin`) Claude Code
  пишет в файл после хука: хук её ещё не видит. Первая версия выключала режим из этого хука и
  выключала его на каждом завершении фоновой задачи; от хука отказались.
- Хуки типа `mcp_tool` подставляют в `input` поля входа хука через `${…}`; отсутствующее поле
  становится пустой строкой (у главного агента `${agent_id}` → `""`).
- Function hooks (проверено `claude plugin validate` и `claude -p --plugin-dir` с
  подставным хабом): `hooks.json` может держать и `hooks`, и `modules`; путь модуля может вести из
  `hooks/` (`../src/mod/register.ts`). `$` разрешено передавать только функциям верхнего уровня
  того же файла, замыкания над `$` — можно; поэтому логика в `commands.ts` получает вызовы движка
  замыканиями и тестируется в bun. `$.http.fetch` до localhost ходит без `Origin`, `$.session.id()`
  совпадает с `session_id` хука SessionStart. `rateLimits` пусты до первого ответа модели; у окна
  200k порог автокомпакта — 167k. `$.command.run` в `-p` после хода недоступен («no session is
  bound»), поэтому `/compact` проверяется только в настоящем окне. `claude plugin test` запускает
  все `*.test.ts` папки плагина, в том числе тесты bun, — не используется.

## Вне объёма

- Подтверждение разрешений из Telegram.
- Команды бота, кроме `/info` и `/compact` (список сессий и т. п.).
